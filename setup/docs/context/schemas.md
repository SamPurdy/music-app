# Data Schemas — Context Reference

> **For local AI agents.**
> Read this before working with data that is stored, passed between components,
> or sent to/from an API. Knowing the exact shape prevents the model from inventing
> field names or types that don't exist.

> ⚙️ **Customize this file as you build.** Delete the example schemas below and
> replace them with your app's actual data shapes. Keep it up to date — a stale
> schema is worse than no schema.

## How to use this file

When the model needs to know the shape of a data object (e.g. to write a component,
map over a list, or call an API), it reads the relevant schema here instead of
scanning multiple source files to infer the shape.

**After creating or changing a type**, update both:
1. `src/types/index.ts` — the TypeScript interface (source of truth for the compiler)
2. This file — the human-readable schema with field descriptions

## Core App Types

> ⚙️ Replace these examples with your app's actual types.
> Copy the TypeScript interface from `src/types/index.ts` and annotate each field.

### AppUser

```ts
// src/types/index.ts
export interface AppUser {
  id: string           // UUID — generated by the server on account creation
  name: string         // Display name — shown in the UI
  email: string        // Email address — used for login; not shown in public UI
  avatarUrl?: string   // Optional. Full URL to avatar image. If absent, show initials.
  createdAt: string    // ISO 8601 date string — "2024-01-15T10:30:00Z"
}
```

**Notes:**
- `id` is always a UUID string — never a number
- `avatarUrl` can be `undefined` — always null-check before rendering an `<img>`
- `createdAt` is always an ISO string — use `new Date(user.createdAt)` to parse

### LoadingState

```ts
// src/types/index.ts — shared across all async components
export type LoadingState = 'idle' | 'loading' | 'success' | 'error'
```

**State machine:**
```
idle → loading → success
                → error → idle (on retry)
```

- Components should show a skeleton/spinner when `status === 'loading'`
- Components should show an error message when `status === 'error'`
- The `idle` state means "hasn't tried yet" (not the same as `success`)

## API Response Envelope

> ⚙️ If your app makes HTTP requests, document the standard response shape here.
> If no backend, delete this section.

```ts
// Shared wrapper for all API responses
export interface ApiResponse<T> {
  data: T | null       // The actual payload — null on error
  error: string | null // Human-readable error message — null on success
  status: number       // HTTP status code
}
```

**Usage pattern:**
```ts
const result = await fetchUser(userId) // ApiResponse<AppUser>
if (result.error) {
  setErrorMessage(result.error)
  return
}
// result.data is now guaranteed non-null
setUser(result.data!)
```

## Watch-Outs

> ⚙️ Add entries here as you discover schema-related bugs.

- **Always use ISO strings for dates** — never pass raw `Date` objects through props or store them in state; they serialize to `{}` in JSON
- **`undefined` vs `null`** — TypeScript distinguishes these; pick one convention and stick to it (this project uses `null` for "explicitly empty", `undefined` for "optional/not set")
- **Array vs single item** — if a field can be either, it's always confusing; prefer always-an-array with a length check
